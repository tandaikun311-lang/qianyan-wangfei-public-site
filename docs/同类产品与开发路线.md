## 二、现有仓库实际状态

这是纯静态前端基础版。已有轮播、产品详情、公开分享链接、Canvas 海报、二维码和底部浮窗导航。

- 产品介绍在 `index.html` 的 `PRODUCT_DETAILS` 中，页面卡片也有一份文案，后续应合并成同一数据源。
- 邀请码请求为相对路径 `api/invite/validate`；仓库没有该后端。没有接口时，有邀请码的生成应显示错误，禁止伪装成验证成功。
- 分享链接目标固定为 `https://tandaikun.com/partner/`，开发环境要注意不要把测试归属写入线上。
- 没有真实登录、我的订单、我的团队、申请审核、余额、结算或财务审批功能。
- 当前“申请合作”跳转分享工具，不构成申请提交；这是优先要接通的业务缺口。
- 图片是现有视觉示意素材，正式商品图片、规格、价格、品牌标识需要品牌方替换并确认。

本次已修复：商品参数链接直接打开对应详情；底部浮窗导航随滚动切换高亮。

## 三、开发顺序

### P0：品牌确认与基础页面闭环

负责人：品牌产品负责人、前端开发、设计。

1. 填写 `品牌确认清单.md`，产品名、规格、正式图片和咨询渠道优先。
2. 商品文案合并为单一数据源；商品可下架，不得通过旧链接继续宣传下架商品。
3. “申请合作”接真实申请接口；提交成功必须得到申请编号，失败可重试。
4. 分享目标域名、接口根路径、联系方式变为统一环境配置；不能在代码里放访问密钥。
5. 完成手机浏览器与微信内置浏览器验收。

交付物：客户可用基础页、有效申请记录、移动端验收记录。

### P1：有身份的伙伴入口

负责人：后端、前端、品牌运营、测试。

1. 登录与退出、会话过期处理；接口从登录态识别本人。
2. 登录后按角色展示“我的订单”和“我的团队”。保持浮窗样式，公开游客仍使用现有基础导航。
3. 我的订单：状态筛选、详情、退款状态；失败显示重试，禁止用演示订单兜底。
4. 我的团队：仅展示本人可访问的直接关系；手机号码等信息脱敏。
5. 邀请来源校验、归属绑定、过期/停用/冲突处理；扫描二维码不直接改变上下级关系。

交付物：真实身份与真实数据贯通，越权访问测试通过。

### P2：订单与账务闭环

负责人：后端、财务、品牌规则负责人、测试。

积分余额→财务确认充值→积分购买→订单履约→奖励流水→退款冲销→结算确认。

上述流程沿用此前项目方向，正式规则仍需品牌方书面确认。金额/比例不预设；不因竞品有多层玩法就扩展本项目层级。充值和审批须以本人独立登录执行，记录操作人、时间、订单、规则版本和前后余额。禁止同一请求重复扣款或重复发奖励。在线支付、自动提现不进入本次范围。

交付物：可追踪账务流水、退款与重复请求测试、备份恢复记录。

## 四、发布方式

先在分支开发，通过 Pull Request 合并；品牌方确认页面和商品材料后出版本。服务器部署是后续独立步骤，不因合并代码自动改线上。保留旧版本、数据备份、回滚说明；基础版与正式交易功能分别验收。
